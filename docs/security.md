# Security — ARTHVEX Mail

## Identity and session controls

- Argon2id password hashing (`@node-rs/argon2`), password policy in `core/password.ts`, per-account
  failed-login lockout after 5 attempts for 15 minutes, constant-time verification for unknown emails.
- Sessions are random 256-bit tokens stored as SHA-256 hashes only. Cookie is `httpOnly`,
  `SameSite=Lax`, `Secure`, `__Host-` prefixed in production, with absolute and idle expiry.
- CSRF: an HMAC token derived from the session id must accompany authenticated writes; browser
  `Origin` must match the configured app origin. Public auth endpoints are exempt from the token rule
  but still subject to Origin checks and rate limits.
- MFA: TOTP with replay protection (time step stored) and ten single-use recovery codes. Admin MFA is
  mandatory in production. Disabling MFA requires the password and a current code.
- Password reset/verification tokens are 256-bit random values stored as SHA-256; single-use,
  expiring, and invalidated on rotation. Recovery codes are stored hashed.
- Platform administrators are a separate principal type with separate sessions, MFA tables and audit
  attribution. There is no schema path from a customer account to platform role.

## Authorization

- `authorizeTenant()` is the single tenant gate: non-members get `404`, insufficient role `403`,
  suspended workspace writes refused. Every subsequent query filters by the authorized tenant id.
- Mailbox operations use `authorizeMailboxAccess()`: `owner`/`admin` may manage mailboxes; a
  `mailbox_user` only reaches the mailbox linked to their membership; everyone else gets `404`.
- Webmail re-authorizes on every request. There is no long-lived content entitlement except a
  grant checked per request.
- Negative tests exercise modified tenant/mailbox ids (see `docs/testing.md`).

## Exceptional mailbox access

Ordinary platform privileges cannot read message content. Access requires:

1. a request by an operator with `admin.access.request`, naming one mailbox and a reason (≥10 chars),
   optionally linked to a support ticket in the same workspace;
2. approval by a **different** super admin (`admin.access.approve`, two-person rule enforced in
   `core/access-grant.ts` and re-checked with a conditional SQL update);
3. read-only scope, 60-minute default TTL (5–240 configurable), no bulk export;
4. audit of request, approval, denial, every use, expiry (worker sweep) and revocation;
5. only the requesting operator can use the grant; revocation/expiry blocks immediately.

The customer privacy policy must disclose that support may access mailbox content for a documented
support or abuse case, under this workflow. Retention: grant metadata and audit rows should be retained
for at least 12 months by operator policy (no automatic pruning is configured); message content is never
copied into the control plane.

## Webmail security

- The Stalwart management credential never reaches the browser. Webmail uses a mailbox-scoped API key
  generated by Stalwart, stored AES-256-GCM encrypted, never returned by any API, revoked with the
  mailbox. It carries only that mailbox's own permissions (no `sys*` management rights).
- HTML is sanitised server-side with a strict allowlist (`sanitize-html`): no scripts, frames, forms,
  objects, event handlers or `javascript:` URLs. Remote images are stripped by default and counted;
  the user can opt in per message/mailbox. Content renders in a sandboxed iframe with
  `allow-popups` only (no scripts, no same-origin access).
- Every search is scoped to one mail folder; there is no cross-mailbox search path.
- Attachments: count, per-file and total size limits, executable extension blocklist, RFC 5987
  filename encoding, `X-Content-Type-Options: nosniff`, `Content-Disposition: attachment`.
- Failed sends keep the draft. A submission that succeeded is not reported as failed merely because
  the Sent-folder copy failed, avoiding duplicate sends.

## HTTP and data protections

- Helmet CSP (`default-src 'none'`, `frame-ancestors 'none'`) for API responses; HSTS in production.
- Request body limit 256 KiB globally; webmail compose routes have a scoped limit derived from
  `WEBMAIL_MAX_ATTACHMENT_BYTES`.
- Zod validation on every route input; centralized error handler hides internals and returns a
  correlation id. SQL uses placeholders only. Logs redact cookies, authorization and CSRF headers.
- Secrets: environment file `0600` on the host, `APP_ENCRYPTION_KEY` and `SESSION_SECRET` generated
  with `openssl rand`. Startup validates key length and refuses unsafe production combinations.
- Audit metadata is redacted for password/secret/token/key/otp/code/cookie/authorization keys.

## Email abuse controls

- Submission requires authentication; there is no open relay configuration in the supplied templates.
- Per-plan daily/hourly send limits and per-mailbox quotas are enforced; outbound abuse reports feed
  the admin abuse workflow and can trigger mailbox/tenant suspension.
- External forwarding requires the destination owner's confirmation before it activates.
- Aliases are loop-checked; catch-all is policy-controlled.

## Production fail-closed checks

Startup throws when any of these is true in `NODE_ENV=production`: development mail adapter, development
mailer, built-in webmail on the development adapter, `COOKIE_SECURE=false`, admin MFA disabled, test
domains allowed, non-HTTPS `APP_BASE_URL`, missing `APP_ENCRYPTION_KEY`/`SESSION_SECRET`, missing
Stalwart credentials when the Stalwart adapter is selected, or an attachment cap above 50 MiB.

## Known limitations

- API-key semantics for Stalwart must be verified against the exact deployed version before enabling
  webmail in production; the management credential needs `impersonate` and `sysApiKey*`.
- No WAF; rely on Apache limits, rate limits and monitoring.
- OpenAPI and deployment templates are hand-maintained and need review on every release.
- Legal pages are drafts and require legal review.
